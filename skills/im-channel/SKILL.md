# 渠道接入

## 何时用这个技能

要在网页之外让用户用微信、飞书、钉钉跟系统对话。

也包括：渠道重复推送导致重复执行、会话串了、回包超时。

## 三个职责

渠道只做三件事，多一件都不做。

收：从平台请求里取出用户标识与文本。

转：归一化成内部请求 `{ channel, userId, sessionId, text }`。

发：把回复发回平台，失败要能重试。

业务判定、金额计算、权限校验全部在运行时，渠道不许碰。

## 会话映射

会话标识用「渠道前缀 + 用户标识」，例如 `wecom:zhangsan`。

不要用平台的消息 ID。消息 ID 每条都不同，会话会碎掉。

不要用时间戳。同一用户隔天说话应该接着上一轮上下文。

需要区分群聊与私聊时，用 `wecom:group:{chatId}:{userId}`。

## 企业微信

两个方向，密钥三个环境变量。

接收走回调地址，需要处理平台签名校验。

发送调应用消息接口，先取 access_token，缓存两小时。

access_token 过期是常见故障，取失败要重试一次再报错。

没有密钥时用 `--dry-run`，把要发的包打印出来，不真发。答辩现场没网也能演示。

## 通用 webhook

适合任何能发 HTTP 的平台。

请求：`{ userId, text, sessionId? }`。

响应：`{ reply, level, auditSeq }`。

约定三条：超时五秒、失败返回 4xx 不要返回 200、响应体必须是 JSON。

## 去重

平台会重推，尤其是超时之后。同一条消息可能到两次。

处理方式：用平台的 messageId 做去重键，缓存十分钟。

重推直接返回上次结果，不重新执行。

这条不做，用户会看到扣两次钱。

## 超时

运行时可能慢（模型调用、外部服务）。平台回调通常五秒超时。

做法：先回「正在处理」，处理完再主动推一条结果。

不要为了赶超时把判定逻辑短路。

## 验收

私聊发一句「查余额」，能收到余额。

同一条消息重推两次，只执行一次。

access_token 过期后能自动恢复。

渠道断开时，网页端仍可正常工作。

## 反模式

在渠道层做金额校验。渠道是传输层，判定必须在运行时。

把平台返回的错误直接抛给用户。要翻译成用户能懂的话。

用轮询拉消息代替回调。延迟高、易重复。

渠道配置写死在代码里。密钥走环境变量，渠道开关走配置。
