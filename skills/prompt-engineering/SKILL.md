# 提示词工程

## 何时用这个技能

要让 AI 改代码、写文档、做评审，但不确定怎么描述才能一次做对。

也包括：AI 反复改不对、改完比改前更乱、一次改五个文件导致无法回滚。

## 四段结构

顺序固定，缺一段就多一轮返工。

```
背景：项目是什么，现在到什么程度。
任务：要做的具体事情，一条一行。
约束：不许做什么，边界在哪。
验收：怎么判断做完了，要可执行。
```

## 上下文分区

项目事实与本次要求要分开写。混在一起 AI 会分不清哪句是数据。

```
【项目事实·只读】
金额统一整数分。工具表在 shared/rules.ts。判定表三条，见 docs/03。

【本次要求·执行】
给判定加日累计维度，单日超过五千元判红。
```

## 给例子，不给形容词

形容词是提示词里最不可靠的东西。

| 写了等于没写 | 换成 |
|---|---|
| 代码要清晰 | 函数不超过四十行，嵌套不超过两层 |
| 异常处理要完善 | 外部调用超时五秒，失败返回 `{ ok: false, error: "external_timeout" }` |
| 界面好看一点 | 三栏布局，左对话右状态，间距 16px，判定用色块不用阴影 |
| 参考一下成熟的写法 | 照 `track-pi/src/agent.ts` 的 confirm 方法结构写 |

## 少样本怎么写

给两条就够：一条反例，一条正例，正例必须能直接抄。

```
反例：判定只返回布尔值，无法解释。
正例：
hits.push({ rule: "single-limit", detail: `金额超过单笔限额 ${limit / 100} 元` });
```

## 约束的写法

约束要写成可判定的句子，不要写成态度。

能判定：「不许引入新依赖」「不许改 `shared/rules.ts` 的导出签名」。

不能判定：「注意代码质量」「保持风格统一」。

## 委派给子代理

模板四行，缺一行就会跑偏。

```
角色：backend 子代理。
范围：只改 track-pi/src/agent.ts，不动 shared/。
任务：把 confirm 的令牌校验从「只比对 token」改成「比对 token 加参数摘要」。
验收：node scripts/smoke.mjs 通过；手工改一次参数后确认失败。
```

## 一次一件事

一次让 AI 改五个文件，出错时无法定位是哪一步引入的。

改完立刻跑 `node scripts/check.mjs`，过了再给下一个任务。

## 返工信号

出现这四种情况，说明提示词有问题，先改提示词再继续。

| 现象 | 原因 | 改法 |
|---|---|---|
| 改了三轮还没对 | 任务太大 | 拆成三个小任务 |
| 改完别处坏了 | 没写范围 | 明确「只改哪个文件」 |
| 输出的不是想要的风格 | 没给例子 | 补一条正例 |
| 反复说「已完成」但跑不起来 | 验收不可执行 | 把验收改成一条命令 |

## 验收一条命令

最好的验收是能直接跑的。

```powershell
node scripts/smoke.mjs
```

比「请确认功能正常」强一百倍。

## 反模式

把整份文档塞进提示词。AI 会抓错重点。只给相关的一段，其余让它按路径自己读。

用「你自己判断」代替约束。判断会飘。

一次要求「顺便优化一下」。顺手改动最难回滚。

不说明现有代码在哪，让 AI 猜。猜错就要重来。

## 给 AI 读文件时的写法

指明路径与用途，不要让它全文搜索。

```
读 track-pi/src/agent.ts 的 confirm 方法（约 60 行），
按它的结构给 chat 方法加一段审计。
不要读 ../../shared 以外的目录。
```
