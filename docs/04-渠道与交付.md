# 渠道与交付

赛题要求系统能通过 APP、IM 等渠道与用户连接。这篇说清两件事：渠道怎么接，交什么。

## 渠道分层

渠道不是业务逻辑，渠道只做三件事：收消息、转内部请求、回消息。

```
企业微信群  →  webhook  →  归一化成 ChatRequest  →  运行时  →  ChatReply  →  webhook 回包
```

归一化后的请求只有四个字段：`channel`、`userId`、`sessionId`、`text`。运行时不知道消息从哪来。

## 企业微信

包里给了 `channels/wecom.mjs`，实现两个方向。

接收：`POST /wecom/callback`，从 body 里取 `FromUserName` 与 `Content`，会话标识用 `wecom:${FromUserName}`。

回复：调企业微信的应用消息接口，把 `ChatReply.reply` 发回去，判定结果拼在后面。

需要的环境变量三个。

| 变量 | 用途 |
|---|---|
| `WECOM_CORP_ID` | 企业标识 |
| `WECOM_AGENT_ID` | 应用标识 |
| `WECOM_SECRET` | 应用密钥 |

没有密钥也能演示：脚本内置 `--dry-run`，把要发的包打印到控制台，不真发。

## 通用 webhook

`channels/generic-webhook.mjs` 适合对接飞书、钉钉、自建 IM。

约定：请求体 `{ userId, text, sessionId? }`，响应体 `{ reply, level, auditSeq }`。

对方只需要能发 HTTP 请求、能展示文本，就能接上。

## 前端

`web/` 是两条路线共用的界面，四个功能。

| 功能 | 交互 |
|---|---|
| 对话 | 输入框回车发送，Shift 加回车换行 |
| 判定展示 | 气泡右上角显示绿黄红，点开看命中的规则 |
| 确认卡片 | 黄色判定时出现，一个按钮确认，一个取消 |
| 审计 | 右侧列出最近记录，显示序号与链校验结果 |

页面必须显示的数字：账户可用余额、最近一条审计序号、链校验状态。

这三个数字是答辩时「系统是真的」的证明。

## 交付清单

提交前对照这份清单，缺一项就补。

### 仓库

- `README.md` 说清项目是什么、怎么跑、架构怎么分层。
- `AGENTS.md` 说清协作规范。
- `CHANGELOG.md` 有完整演进记录。
- `.gitignore` 排除依赖、构建产物、数据目录、密钥文件。
- 无任何真实密钥、内网地址、真实用户数据。

### 演示

- 三分钟视频，顺序固定：正常办理、越权拦截、注入拦截、扩展能力。
- 视频里能看到判定颜色与审计序号。
- 视频不要配背景音乐，要能听清讲解。

### 自述

三段结构。

第一段说做了什么：六个场景里做了几个，分别是什么。

第二段说怎么验证：测试多少条，拦截率多少，怎么复现。

第三段说不足：哪些没做，为什么没做，如果多给两天会怎么做。

第三段最容易得分，也最容易写砸。不要写「时间不够」，要写「这个能力需要 X，当前方案在 Y 上有缺口」。

### 现场答辩

评委常问五个问题，提前准备。

| 问题 | 回答要点 |
|---|---|
| 判定为什么是黄色 | 指出命中的具体规则与阈值 |
| 模型乱说要转账怎么办 | 说明判定在代码层，模型只产意图 |
| 怎么证明审计没被改过 | 现场改一条再校验，展示失败 |
| 新增一个场景要改多少 | 说清三步：契约、判定、执行 |
| 和直接用大模型有什么区别 | 说清权限分级与可解释性 |

## 提交前最后一遍

```powershell
node scripts/check.mjs
node scripts/smoke.mjs
git status
```

第一个看结构，第二个看功能，第三个看有没有漏提交的文件。

三个都干净再提交。提交后打标签 `v1.0.0`。
