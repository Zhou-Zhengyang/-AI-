# 两条路线怎么选

这篇帮你十分钟内做完决定。

## 一句话区别

Cordis 管的是「谁提供服务」，pi 管的是「谁处理这一轮」。

前者把能力拆成服务，靠上下文注入把它们连起来。后者把一轮对话拆成状态、传输、扩展三段，靠钩子串起来。

## 只剩下三天怎么办

直接选 pi，不用看决策树。

理由三条：代码量少一半，改一处立刻见效，出问题能在一个文件里定位。省下来的时间投到三色判定与演示录屏上，那才是评分主线。

Cordis 的价值在多人协作与长期演进，三天来不及把它的好处用出来。

## 决策树

如果你有五天以上，按顺序回答四个问题，第一个「是」就是你的答案。

**问题一：团队超过两人，并且要并行改不同模块？**
是，走 Cordis。服务的边界天然适配分工，两个人改两个服务不会互相覆盖。

**问题二：要在答辩里重点讲架构分层与扩展性？**
是，走 Cordis。注册表、服务声明、插件热插拔，这三样看一眼就懂。

**问题三：你更习惯「改一个文件立刻看到效果」？**
是，走 pi。三段式里每一段都是独立文件，改完重启即可。

**问题四：剩下的时间不足四天？**
是，走 pi。代码量更少，跑通更快。

四个都否，走 Cordis，因为它更容易在答辩时讲清楚。

## Cordis 路线长什么样

核心是 Context。所有能力以服务形式挂在上下文上，插件通过 `ctx.plugin()` 装载，通过 `ctx.effect()` 声明清理动作。

```
Context
├─ ctx.llm        模型调用
├─ ctx.tools      工具注册与执行
├─ ctx.policy     三色判定
├─ ctx.session    会话状态
├─ ctx.audit      审计链
└─ ctx.channel    渠道适配
```

插件之间的依赖通过 `inject` 声明，缺依赖就不启动。这条约束在多人协作时特别有用：谁的插件坏了，启动时立刻暴露。

适合讲的点：服务注册表、依赖注入、生命周期清理。

不适合的地方：写第一个对话框之前，要先理解 Context 与 Service 的关系，大约需要两小时。

## pi 路线长什么样

核心是 Agent。三段职责清晰。

```
Agent（状态 + 事件）
├─ Transport    管模型：发请求、收流、重试
├─ Extension    管能力：工具、策略、审计
└─ Hook         管时序：调用前拦截、调用后记账
```

状态集中在 Agent 里，事件按生命周期发出。想加一条拦截规则，写一个 `beforeTool` 钩子即可，不用改主循环。

适合讲的点：钩子链、状态机、可插拔扩展。

不适合的地方：三段边界要靠自觉守，团队大了容易互相越界。

## 两条路线的共同点

这些不用选，两条都有，且必须都有。

| 能力 | 位置 |
|---|---|
| 意图解析 | `skills/bank-intent/` |
| 三色判定 | `skills/risk-arbitration/` |
| 审计链 | `skills/audit-chain/` |
| 外部服务 | `mcp/` |
| 渠道适配 | `channels/` |
| 前端 | `web/` |

换路线只换 `track-*` 目录，其他照用。

## 迁移成本

先走 pi，中途想换 Cordis，代价是把 `agent.ts` 里的循环拆成服务与插件，约一天。

先走 Cordis，中途想换 pi，代价是把服务收敛成扩展，约半天。

两条路线都跑过再选的团队，通常留 Cordis。

## 确认清单

动手前核对五条。

- 已读完本包 `AGENTS.md`。
- 已跑通 `node scripts/check.mjs`。
- 已选定路线，并在 `CHANGELOG.md` 记下决定与理由。
- 团队对「谁负责哪个目录」有共识。
- 知道出问题时先跑自检再改代码。
