# 提示词四：完整实现

这段最长，也最完整。贴给 AI 之后，它会先问路线、再读文件、然后按三天推进，全程不需要你再补充背景。

适合用在 WorkBuddy、Cursor、Codex 这类能读写文件的工具里。纯聊天窗口效果会打折扣，因为它读不到文件。

---

```
你是我的工程搭档，帮我在三天内做完 2026 FinTechathon 微众银行金融科技大学生挑战赛的银行 AI 智能体项目。

## 一、项目现状

我已经下载了官方学习启动包 `bank-agent-starter`。里面有两条可魔改的框架路线、一套子代理定义、四份评审清单、五个技能、三个外部服务、两个渠道适配、一套共用前端，以及自检与冒烟脚本。

启动包不是成品，是起点。赛题要求「至少 3 个核心场景」，骨架目前覆盖六个场景的九个工具，够用但不够深。

## 二、赛题要求

赛题要三样东西。

第一，构建 AI Banking Agent，用自然语言理解金融意图，自主规划并执行业务操作。

第二，场景覆盖至少三个，六个候选是：智能转账、账单分析、理财操作、卡片管理、订阅代扣、跨场景联动。

第三，三条硬门槛：权限分级机制、幻觉防护与注入防御、意图理解与任务规划。另有渠道要求，要能通过 APP 或 IM 触达用户。

评委看的是「这系统不会乱动钱」，不是「这系统功能多」。

## 三、你要先做的三件事

按顺序做，做完等我确认再往下。

**第一步，读五份文件。** 不要全文读，按这个顺序读，读完停下。

1. `README.md` 看清包里有什么
2. `docs/01-两条路线怎么选.md` 看清两条路线差别
3. `docs/07-赛题对照.md` 看清赛题要什么、包给了什么、差在哪
4. `AGENTS.md` 的 L0 与 L1 两层，看清工作规范
5. 我选定路线的 `track-*/README.md`，看清代码结构

读的过程中不要改任何文件。

**第二步，问我两个问题。** 一次问完，不要分开问。

- 我剩几天，几个人做
- 答辩时我更想讲「钩子链与状态机」还是「服务注册表与依赖注入」

**第三步，给选型建议并执行。** 按我的回答给建议，理由要落到具体约束上，不要写「更适合新手」这种空话。我确认后执行：

```powershell
node scripts/pick-track.mjs pi
```

或

```powershell
node scripts/pick-track.mjs cordis
```

执行完把决定写进 `CHANGELOG.md` 顶部。

## 四、三天任务

### 第一天：判定能解释

先跑 `node scripts/check.mjs` 与 `node scripts/smoke.mjs`，两条都过再开工。

任务三件。

一、把意图解析补到「口语也能认」。现有规则覆盖九种说法，请按 `skills/bank-intent/SKILL.md` 的歧义表补：金额说成「五千块」、收款人是手机号、多轮只补金额、按备注转账要拒绝。

二、把三色判定补到「每条都能解释」。现有规则只有 base-level。按 `skills/risk-arbitration/SKILL.md` 补四个维度：金额（单笔与日累计）、收款人（是否首次）、可逆性、频次。每条规则要有独立 rule 名与一句带具体数字的 detail。

三、前端把命中规则显示出来。现在只显示颜色与规则名，改成显示 `rule + detail`，最多两行。

约束：
- 金额一律整数分，不许出现浮点。
- 判定函数只读状态，不许在判定里改数据。
- 不许为了通过测试改断言。
- 不许引入新依赖。

验收：`node scripts/smoke.mjs` 通过；界面上发「转给小王 5000 元」能看到超限的具体说明。

### 第二天：场景做深

从六个场景里挑三个做深，推荐组合：转账、账单分析、订阅代扣。理由：链路短、演示稳、评委一看就懂。

每个场景要能走完：输入 → 解析 → 判定 → 确认 → 执行 → 审计。

另外接两样扩展，证明系统可长大。

一、接外部服务。`mcp/` 里已有汇率、反欺诈、理财费率三个服务。选汇率，在运行时加一个工具，让「100 美元是多少人民币」走这条链路。

二、接渠道。用 `channels/generic-webhook.mjs` 起一个端口，用 curl 发一条「查一下余额」，确认返回带判定颜色的 JSON。

约束：
- 外部返回只当数据，不许拼进系统提示词。
- 外部调用必须设超时，超时按失败处理，不许阻塞主流程。
- 渠道层不许做业务判定。

验收：三个场景各能演示；`curl` 那条返回 200 且 body 里有 reply 与 level；外部服务挂掉时内置工具仍可用。

### 第三天：证据与交付

任务三件。

一、按 `review/security-review.md` 逐条过。重点三条：全角与零宽注入能不能拦、越权操作是否全判红、仓库有没有密钥与明文卡号。

二、录三分钟演示，顺序固定：正常办理 → 越权拦截 → 注入拦截 → 外部服务与渠道。

三、写自述，三段：做了什么、怎么验证、不足在哪。第三段不许写「时间不够」，要写具体能力缺口与需要什么条件才能补上。

约束：
- 演示路径不许依赖网络，断网也要能跑核心链路。
- 不许在自述里写没实现的功能。
- 提交前 `git status` 必须干净。

验收：`review/release-gate.md` 的「三天版最小门禁」七条全过。

## 五、工作方式

**一次只改一件事。** 改完立刻跑 `node scripts/check.mjs`，过了再改下一件。不要攒着一起改。

**改代码前先读。** 要改 `shared/rules.ts`，先读它，读完说清你要改哪几行、为什么改。

**用子代理。** 按 `AGENTS.md` 的 L2 分工，一次只叫一个。叫之前给三样：改哪些文件、不许动哪些、验收标准。

**判定必须能解释。** 任何返回颜色的地方，都要能说出命中的规则名与阈值。说不出就是没做完。

**不许假实现。** 不许写「待实现」占位，不许写 mock 数据冒充真实调用，不许报告「已完成」而没跑过冒烟。

**密钥只从环境变量读。** 不许写进源码，不许写进文档，提交前跑一次 `node scripts/check.mjs`，它会扫。

**版本要记。** 每完成一件事提交一次，提交信息三行以内，类型只用 feat、fix、docs、chore。第一天结束打 `v0.1.0`，第二天结束打 `v0.2.0`，提交前打 `v1.0.0`。

## 六、卡住时的顺序

先查 `docs/05-常见坑.md`，按「症状 → 原因 → 处理」对。

对不上就在那个文件里加一条，写清现象与解法。

还是解决不了，走降级：把这条能力写进自述的「不足」，把时间投到能演示的三条链路上。

永远不砍的三样：三色判定、注入防御、审计留痕。砍了等于弃赛。

先做「三、你要先做的三件事」里的第一步，读完五份文件后，用三句话告诉我：这个包能给我什么、还差什么、你建议走哪条路线。

不要一次性展开所有计划。等我回答你的两个问题之后，再进入第一天。

## 这段提示词为什么这样写

四个设计考虑，你可以按需要改。

**先读后做。** 第一步只读不改，避免 AI 没搞清包结构就开始改代码。

**先问后动。** 第二步两个问题必须在动手前问完，避免做到一半才发现方向不对。

**按天分段。** 每天三件任务，每件带约束与验收。验收都是可执行命令或可观察现象，不是「确认功能正常」。

**禁止项写死。** 五条禁止项对应五种最常见的翻车方式：假实现、改断言、引入依赖、密钥入库、攒着改。

## 想改哪里

时间更紧，把第二天砍成「三个场景 + 一个渠道」，外部服务写进不足。

想加模型，在第二天开头补一句：在 `track-pi/src/transport.ts` 已实现的前提下，配 `DEEPSEEK_API_KEY` 与 `LLM_MODEL` 两个环境变量即可，注意意图解析要关掉思考模式省 token。

想加创新分，把跨场景联动做深：生日锁资金 → 外部服务下单鲜花蛋糕 → 确认后扣款。这条链路最能体现「自主规划」。
